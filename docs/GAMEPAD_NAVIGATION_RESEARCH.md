# Controller navigation research base

Web-only research, no project files touched. Bullets marked **[inference]** are my own synthesis, not a direct claim from the cited source — everything else is stated by the source.

## 1. Established best practices

**General accessibility guideline bodies**
- Game Accessibility Guidelines (GAG) has no single "menu navigation" category — it organizes by impairment type (Motor/Cognitive/Vision/Hearing/Speech) and severity (Basic/Intermediate/Advanced). The full list fetched from https://gameaccessibilityguidelines.com/full-list/ contains no guideline that names focus memory, wrap-vs-clamp, or hover-tooltip equivalents explicitly. The closest applicable ones: "Ensure that all areas of the user interface can be accessed using the same input method as the gameplay" (Motor, Basic), "Support more than one input device" (Motor, Intermediate), "Give a clear indication that interactive elements are interactive" (Cognitive/Vision, Intermediate), "Allow controls to be remapped/reconfigured" (Motor, Basic). Source: https://gameaccessibilityguidelines.com/full-list/. **I could not verify GAG has specific controller-menu-navigation guidance** — it's aimed lower-level than that.
- Xbox Accessibility Guidelines (XAGs): I could not retrieve the guideline document text itself (the guideline page 404'd from both attempted URLs). What is verifiable is the program's existence and scope: XAGs launched January 2020, built by Microsoft's Gaming Accessibility team starting 2019, meant "to be used by designers to generate ideas and as a guiding checklist for validating the accessibility of a game," and have since been expanded to include motion-sickness reduction, on-screen text legibility, contrast, and input guidance. Source: https://news.xbox.com/en-us/2021/02/16/xbox-accessibility-guidelines-and-testing/. **Could not verify** specific rules on initial focus, focus memory, or tooltip equivalents from Microsoft directly — treat any such claim as unsourced.

**Unity's own documentation**
- `InputSystemUIInputModule` is Unity's "drop-in replacement" for the legacy `StandaloneInputModule`, driving UI input through the Input System instead of the legacy Input Manager. Source: https://docs.unity3d.com/Packages/com.unity.inputsystem@1.7/manual/UISupport.html.
- Unity auto-offers to replace `StandaloneInputModule` with `InputSystemUIInputModule` in the Inspector once the Input System package is installed. Same source.
- "Deselect on Background Click": by default, clicking with no GameObject hit clears the current EventSystem selection; this is a toggleable property on the input module. Same source. This is exactly the "back button is Escape-only / mouse click ruins gamepad focus" failure mode described in the brief.
- Move Repeat Delay (initial delay before repeat) and Move Repeat Rate (interval between repeats, capped by frame rate) are the two timing knobs Unity exposes for stick/d-pad-driven UI navigation repeat. Same source.
- Unity's own navigation modes (Automatic/Horizontal/Vertical/Explicit) are documented at https://docs.unity3d.com/Packages/com.unity.ugui@1.0/manual/script-SelectableNavigation.html (confirmed to exist via Unity Discussions links, not independently re-fetched in this pass).

**Community-documented pitfalls (Unity Discussions / forum.unity.com)**
- Automatic navigation mode is widely reported as unreliable: users describe overlapping or oddly-spaced Selectables causing navigation to "skip" the intended neighbor for a farther one, and describe the algorithm as "working only about half the time" in some layouts. Sources: https://discussions.unity.com/t/ui-auto-navigation-choosing-wrong-selectables/1667758, https://discussions.unity.com/t/bad-automatic-navigation-between-selectables/225159, https://discussions.unity.com/t/trivial-glitch-on-ui-automatic-selectable-navigation/950551.
- The commonly cited workaround is switching to Explicit navigation, but a reported side effect is that pointing Explicit navigation at a Selectable that is sometimes non-interactable breaks that link. Source: same thread cluster above.
- Clicking empty space clearing the current selection is a long-standing, explicitly requested-against behavior: a multi-page Unity Discussions feature request ("option to disable deselect in UI Input Module") exists specifically because this breaks gamepad navigation after any mouse click on blank space. Sources: https://discussions.unity.com/t/feature-request-option-to-disable-deselect-in-ui-input-module/761974, https://discussions.unity.com/t/ui-navigation-breaks-if-you-deselect-all-objects-with-mouse-or-touch/731198.
- A related Unity Issue Tracker entry: "Deselect On Background Clicks" doesn't fully work under UI Toolkit even when disabled, and disabled controls being hit still null out selection. Source: https://issuetracker.unity3d.com/issues/disabling-the-deselect-on-background-clicks-option-in-input-module-component-doesnt-work-when-using-uitoolkit.
- Setting the initial focus is done via `EventSystem.firstSelectedGameObject`, or programmatically via `EventSystem.current.SetSelectedGameObject(...)`, and the community pattern for "screen-specific first focus" is to call `SetSelectedGameObject` in `OnEnable()` of the screen so each screen chooses its own starting focus rather than relying on one static Inspector field. Source: https://discussions.unity.com/t/how-to-programmatically-set-first-selected-item-in-event-system/937982 and https://docs.unity3d.com/2018.3/Documentation/ScriptReference/EventSystems.EventSystem.SetSelectedGameObject.html.
- ScrollRect does not auto-follow the selected child; the standard community pattern is a helper component that listens for the EventSystem's selection changing, checks if the new selection's RectTransform is outside the ScrollRect viewport, and adjusts `normalizedPosition`/`content.anchoredPosition` to bring it into view. Sources: https://discussions.unity.com/t/scrollrect-how-to-autoscroll-on-button-navigation/692548, https://discussions.unity.com/t/auto-scrolling-to-a-selected-ui-element/1556645, https://earlycoffee.games/blog/2021_12_30_navigablescrollrect/, https://anja-haumann.de/unity-scroll-rect-controller-input/.
- Device-switch detection pattern: with the new Input System, `PlayerInput` exposes control-scheme switching via `InputUser.onChange` firing `InputUserChange.ControlSchemeChanged`; the common glyph-swap architecture keys off "device kind" independent of "input mode" so glyphs update live without touching gameplay logic. Sources: https://discussions.unity.com/t/detect-most-recent-input-device-type/760071, https://discussions.unity.com/t/last-used-device-x360-xone-ps4-dualsense-etc/859088.
- Mixing both input modules on one EventSystem is a documented footgun: leaving the legacy `StandaloneInputModule` in place alongside `InputSystemUIInputModule` causes unpredictable selection/priority conflicts; guidance is to fully remove the old module. **[low-confidence synthesis of forum discussion, not a single canonical source]** — see https://forum.unity.com/threads/input-class-vs-standalone-input-module-vs-event-system-vs-input-manager-vs-manual-vs-google-v-reddit.473403/.

**Steam Deck Verified (Valve, verifiable via Steamworks partner docs)**
- Controller glyphs "must match the inputs being used, whether it's Deck, Steam Controller, or Xbox glyphs," and "mouse and keyboard glyphs should not be shown if they are not the active input" — interacting with Deck/Steam Controller inputs under the default config must never show non-controller glyphs. Source: https://partner.steamgames.com/doc/steamhardware/compat.
- Valve recommends using the Steam Input API specifically because it handles automatic glyph correction for you. Same source.
- Default controller configuration must let a player reach all content without changing in-game settings first. Same source.
- Any required text entry must go through the Steamworks on-screen-keyboard API or ship a built-in controller-driven text input covering the player's language. Same source.
- Deck-specific legibility rule: smallest on-screen font must not fall below 9px at 1280x800 and must read at ~30cm viewing distance; Valve's own recommendation is 12px+ with user-adjustable size. Same source. **[Not a controller-navigation rule per se, but frequently gates verification alongside input rules — relevant because this project already has a hover-tooltip/glyph gap.]**

**Target selection, drag-and-drop, and modal focus** — I could not find an authoritative written guideline (GAG/XAG/Valve) that names these directly; what's below comes from the shipped-game evidence in section 2, and should be read as **[inference from precedent]**, not codified best practice:
- Turn-based target selection on a pad is near-universally implemented as directional-cycle-through-a-filtered-list (index into valid targets, d-pad/stick to advance) rather than a free cursor. This shows up independently in a Godot-forum worked example (https://forum.godotengine.org/t/targeting-system-in-a-turn-based-rpg/59685) and in FFXIV's controller target-cycling documentation (https://www.akhmorning.com/resources/controller-guide/controller-targeting/), which are different games/engines converging on the same shape — reasonable evidence this is close to a de facto standard, but neither source frames it as a guideline.
- Drag-and-drop equivalents ("pick up with confirm, move focus, put down with confirm again") are not documented in any guideline source found; this is a pattern this project will have to design fresh. Flag this to the owner rather than treat it as solved.

## 2. Critically acclaimed games — verified per-title

- **Baldur's Gate 3** — Larian's own account (PlayStation Blog, official/primary source): radial menus bound to R1/RB, DualSense adaptive-trigger integration where a light pull "peeks" the radial and a hard press past a resistance point locks the selection in, plus radial customization. Source: https://blog.playstation.com/2023/09/05/how-baldurs-gate-3-adapts-its-expansive-rpg-gameplay-for-your-dualsense-controller/. **Documented criticism**, not just grumbling: a dedicated review piece describes the stick input registering as an ambiguous white dot instead of a directional arrow, action selection sometimes needing "upwards of eight tries a turn," and calls radial menus "already a cumbersome method of navigating" even before the bug. Source: https://www.thegamer.com/baldurs-gate-3-radial-menus-trash-controller-borked/. Net: praised for ambition and trigger-integration, criticized for reliability of the core radial input itself.
- **Divinity: Original Sin 2** — controller scheme is built entirely around radial menus (opened via triggers) covering skills/items/actions in place of a hotbar; community sentiment is split between "the radial isn't so bad, wish they'd used that more" and it becoming "fast and intuitive" once muscle memory forms. Source: Steam Community discussion threads surfaced via search, https://steamcommunity.com/app/435150/discussions/0/1519260397773368262/ and related. This is community opinion, not a press review — weight it lower than the BG3 sourcing above.
- **Darkest Dungeon (console ports)** — this is a **negative** precedent worth keeping, not a positive one. Reported specific complaint: navigating hero lists required holding R2 continuously with no cursor equivalent; players on Switch called it "a mouse UI with gamepad controls lazily injected." The developer's own response (as reported secondhand) said the held-button requirement was a deliberate tradeoff because there was no controller cursor and d-pad list traversal felt better than analog-stick-as-cursor. Source: aggregated Steam Community / NeoGAF threads, https://steamcommunity.com/app/262060/discussions/0/3158705742081007784/, https://www.neogaf.com/threads/darkest-dungeons-ui-is-the-biggest-piece-of-garbage-i-have-ever-experienced.1325612/. **This is community-sourced, not a press citation for the dev quote — flag as lower confidence**, but directly useful as a documented anti-pattern (retrofitting a mouse-first UI onto a pad rather than designing pad-first).
- **Into the Breach** — UI was "designed with controllers in mind," left stick acts as a cursor replacement with tile-snapping that centers on the nearest grid cell, described as scaling well across resolutions. Source: search-aggregated (Steam news/GameUIDatabase); a mobile-version review separately notes the port shows Xbox glyphs even under DualSense with no haptics, i.e. glyph-detection was not carried over to that port. Source: https://toucharcade.com/2022/07/21/into-the-breach-mobile-review-controller-support-icloud-save-cross-progress-netflix-games-download-android/.
- **Persona 5 / Royal** — menus map one battle command to one face button (not d-pad cycling), with button glyphs color-matched to the physical controller, explicitly framed by commentary as a "don't make me think" minimal-cognitive-load choice; color choices reportedly break from the game's own art palette specifically to stay legible as button prompts. Source: https://medium.com/@fruitcupkun/persona-5-menus-with-personality-and-readability-d6db2e0b253e (design-analysis blog, not primary/developer source — treat as informed commentary, not confirmed dev intent).
- **Balatro** — native gamepad support for Xbox/DualSense/DualShock/generic DirectInput pads, but two **documented weaknesses**: glyphs are reportedly Xbox-style regardless of the physical pad connected, and "the two input modes (mouse and gamepad) have entirely different ways of selecting UI elements that can't easily coexist" per community reports — i.e. mixed mouse+gamepad use is not well supported. Source: aggregated Steam Community discussion threads found via search (no single canonical review located; treat as community-sourced, moderate confidence).
- **Monster Train** — controller support shipped later via a dedicated "Controller and Keyboard Update," described post-update as "surprisingly slick to control on console," but with a named UI defect: on Switch/Steam Deck, hovering/selecting a card in play can trigger a tooltip/details popup that obscures the board, reported as "irritating" but "manageable." Source: https://store.steampowered.com/news/app/1102190/view/2906474991121580950 (official patch announcement) plus Steam Community reports, https://steamcommunity.com/app/1102190/discussions/0/3488626756863245645/. This is a directly relevant precedent for this project's own hover-only tooltip problem: an automatic-on-focus tooltip can itself become an obstruction if not gated or positioned carefully.
- **Slay the Spire, Hades, Fire Emblem: Three Houses, Octopath Traveler, Dead Cells, Celeste, Inscryption, Monster Train's deck-building specifics** — **dropped or downgraded**: I could not find a specific, sourceable description of Slay the Spire's card-focus/L1-R1 cycling scheme (only forum bug reports about it partially breaking, e.g. controller card selection sometimes limited to the top two rows: https://steamcommunity.com/app/646570/discussions/0/1642044369665273759/); nothing citable on Fire Emblem: Three Houses, Octopath, Dead Cells or Celeste's menu-navigation specifics turned up. For Hades, I confirmed Supergiant discusses UI/menu *animation and world-building intent* (https://x.com/supergiantgames/status/1319314729580462080) and that creative director Greg Kasavin has given GDC talks on Hades' narrative/roguelike design (https://www.gamedeveloper.com/design/watch-greg-kasavin-discuss-the-development-of-supergiant-games-i-hades-i-), but **found no source substantiating specific controller-navigation mechanics** (boon-pick focus behavior, codex list navigation) — despite this being one of the games named as a candidate. Do not cite Hades as a verified controller-UI exemplar beyond "acclaimed for UI presentation generally"; the controller-specific mechanics claim is unverified.

## 3. Unity-specific: StandaloneInputModule vs InputSystemUIInputModule

- `InputSystemUIInputModule` is positioned by Unity as the direct successor, using the Input System package instead of the legacy Input Manager; Unity's Inspector offers one-click migration from an existing `StandaloneInputModule`. Source: https://docs.unity3d.com/Packages/com.unity.inputsystem@1.7/manual/UISupport.html.
- Running both modules on the same EventSystem GameObject causes conflicts — selection/processing order between them is not reliable, and one can block the other. This is reported as a common source of "why did my UI stop responding to gamepad" bugs after a partial migration. Source: aggregated from https://forum.unity.com/threads/input-class-vs-standalone-input-module-vs-event-system-vs-input-manager-vs-manual-vs-google-v-reddit.473403/ and the Input System GitHub PR discussion at https://github.com/Unity-Technologies/InputSystem/pull/1082 (that PR itself, "Redo much of InputSystemUIInputModule," is Unity's own record of behavioral regressions being fixed relative to `StandaloneInputModule`, e.g. pointer-position handling differing because the new module reads per-device values instead of the legacy module's single aggregate `Input.mousePosition`).
- Scroll speed regression: scrolling was reported slower under `InputSystemUIInputModule` than the legacy module, fixed in Input System package version 1.14. Source: https://docs.unity3d.com/Packages/com.unity.inputsystem@1.14/changelog/CHANGELOG.html (referenced via search; not independently re-fetched line-by-line in this pass).
- `Deselect On Background Click` exists on both modules' settings but is the exact mechanism behind "gamepad focus is destroyed by an incidental mouse click on empty space" — the fix is disabling that flag, not working around it downstream. Source: https://docs.unity3d.com/Packages/com.unity.inputsystem@1.7/manual/UISupport.html and the Issue Tracker entry above.
- Community pattern for "first selected on enable": rather than relying solely on the EventSystem's single static `First Selected` field (global, one screen only), the standard approach is a small reusable component on each screen root that calls `EventSystem.current.SetSelectedGameObject(target)` in `OnEnable`, so every screen owns its own initial focus target. Source: https://discussions.unity.com/t/how-to-programmatically-set-first-selected-item-in-event-system/937982.
- Community pattern for "focus-follows-selection scrolling": a `ScrollRect` helper that listens for `EventSystem` selection changes and repositions `content` when the new selection's rect falls outside the viewport — there is no built-in Unity component for this; every source found is a bespoke or community asset. Sources: https://earlycoffee.games/blog/2021_12_30_navigablescrollrect/, https://anja-haumann.de/unity-scroll-rect-controller-input/, https://discussions.unity.com/t/scrollrect-how-to-autoscroll-on-button-navigation/692548.
- Community pattern for device-switch detection: use `PlayerInput`'s control-scheme change notification (`InputUser.onChange` / `InputUserChange.ControlSchemeChanged`) as the single source of truth for "what device is active right now," and drive glyph-swap UI off device *kind* rather than off gameplay input mode, so glyph logic doesn't get entangled with gameplay state machines. Source: https://discussions.unity.com/t/detect-most-recent-input-device-type/760071.
- Automatic navigation mode is flagged repeatedly by the Unity community as unreliable enough that Explicit navigation is the commonly recommended fallback for hand-authored screens, at the cost of having to keep explicit links in sync when a screen's layout changes and of breaking when a linked Selectable becomes non-interactable at runtime. Sources: https://discussions.unity.com/t/ui-auto-navigation-choosing-wrong-selectables/1667758, https://discussions.unity.com/t/bad-automatic-navigation-between-selectables/225159. Given this project's screens are generated by `UiEmitter`/`ScreenRegistry` rather than hand-placed, **[inference]**: Explicit navigation generated programmatically from the same declared tree that lays out the screen is likely a better fit than Automatic, since the generator already knows the intended reading order and won't be subject to the geometric-overlap misfires reported above.

## Notes on what could not be verified
- No direct guideline text was retrievable from Microsoft's Xbox Accessibility Guidelines document itself (only secondary coverage of the program's existence/history).
- No guideline source (GAG, XAG, Valve) explicitly codifies "focus memory when returning to a screen," "wrap vs clamp," or "hover-equivalent for tooltips" as named rules — these are your own team's problem framing, not directly lifted from a published standard. Treat section 1's coverage of those specific sub-topics as **[inference from adjacent rules and shipped-game precedent]**, not as quoted guideline text.
- Hades', Fire Emblem: Three Houses', Octopath Traveler's, Dead Cells', Celeste's and Inscryption's controller-menu mechanics could not be substantiated with a citable source and are dropped from the acclaimed-games list rather than asserted from memory.
- Slay the Spire's specific L1/R1 card-cycling scheme (as it may exist in-game) could not be confirmed by a citable source; only bug reports about a *broken* card-selection state were found.
