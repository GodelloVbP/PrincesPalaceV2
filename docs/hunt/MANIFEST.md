# Hunt manifest

The ledger for the total bug hunt (`plans/ah-can-you-do-binary-hippo.md`). It
is a list of OBLIGATIONS, not of bugs. Finding nothing in a file is a result;
not having looked is the thing this file exists to make impossible to hide.

The row set below is generated from `git ls-files` by `tools/hunt_manifest.py`,
so no scoped file can be missing from it. The judgement cells -- `owner`,
`status`, `evidence`, `revision`, `invalidated-by` -- are written by hand and
carried across every regeneration. The hand-authored sections after the end
marker (cross-file obligations, the clearance ledger) survive regeneration too.

**Status values.** `open` (nobody has taken it), `assigned`, `evidence
recorded` (the row's `evidence`, `revision` and `invalidated-by` cells are
filled), `unresolved` (with a stated reason: environment, timing, needs an
owner decision, out of budget), `re-open` (written by the script when the file
has moved past the revision its evidence was recorded against).

**Evidence kinds**, never conflated: `static read` (a person read the file
against its stated intent), `executed` (the path ran under a test, the bot or
a capture), `asserted` (an assertion checked the behaviour and was seen to fail
when the behaviour was broken). Only `asserted` counts as verified. Write the
kind INTO the evidence cell, with what was run: `asserted: FooTests.Bar`,
`static read; blind spot: reflection`.

**Flags** are derived, and two of the three are lexical over-approximations:

- `never-named` -- the file's stem (dots included, so `FightSession.Enemies` is
  its own obligation) appears as a whole word in no file under
  `Scripts/Tests/`. 50 files today, which is the plan's inventory number.
- `lifecycle` -- a Core `.cs` mentioning `Update`/`LateUpdate`/`FixedUpdate`/
  `OnEnable`/`OnDisable`/`OnDestroy`/`StartCoroutine`/`IEnumerator`. 59 files,
  against the plan's 49 "lifecycle controllers": the extra ten are files whose
  match is a plain `IEnumerator` return or a method named `Update` that is not
  a Unity message (`ContentDatabase.Effective.cs` is one). The flag decides
  which rows require `asserted`; `docs/hunt/SCENARIOS.md` decides what is
  actually driven.
- `seam` -- a file belonging to one of the four seams. Their CROSS-FILE
  obligation (every call site read) is below the generated block; the flag on
  the file row is only the callee half.

Files: `docs/hunt/README.md` (how to regenerate), `docs/hunt/SCENARIOS.md`
(the Stage 3b lifecycle scenarios).

## Clearance ledger

Every mechanism the two hunt records and the four 2026-09-10 finder reports
list as "looked at, clean". A ledger row is a clearance of a MECHANISM at a
REVISION under a METHOD, and it EXPIRES when its invalidator lands -- at which
point the mechanism goes back on the hunt whether or not anybody has a new
repro. Re-review is permitted on an expired row without one.

**Revisions recorded here are the hunt RECORD's commit, not the commit each
finder actually read.** `24527ba5` is the last commit of the 2026-09-08
write-up; `59dca3db` is the 2026-09-10 record and is HEAD. A finder read its
slice at some commit at or before those, so a row's real revision is no LATER
than the one recorded, which is the conservative direction: the script will
re-open a row whose file has moved since, and will not fail to re-open one
that should have been.

**Method is what the finder actually did.** Almost every row below is `static
read` -- a person read the mechanism against its stated intent. Where an
existing test pins the behaviour and the finder re-derived its literals, the
method says so; that is `asserted` cover the hunt did not add, and it is
recorded separately from the reading.
