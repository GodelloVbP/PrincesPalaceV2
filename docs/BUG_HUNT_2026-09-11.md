### Task 2 — existing lints and validators: blind spots

Method: each lint's own source read once against its stated intent, plus
`tools/test.ps1 ui,content,art` (EditMode 11 passed, PlayMode 270 passed / 23
skipped, dotnet 1631 passed, 0 failed). Full per-lint blind-spot text is in
the manifest evidence and `stage2/lints/blindspots.md`; the shape repeats
across three families:

- **UI construction lints** (`UiAudit`, `UiTextFitAudit`, `UiWiringSweep`,
  `UiCountAudit`, and their test-embedded siblings) each audit a
  BUILD-TIME snapshot -- a solved tree, a serialized reference, an authored
  sample string. None can see a runtime mutation after the scene is built
  and running (a controller resizing a `RectTransform` mid-fight, a
  destroyed-then-fake-null reference, content-derived text of unbounded
  length). `UiWiringSweep` additionally only descends one level into a
  nested serializable struct. `ButtonFallbackLintTests` restates
  `EmitButton`'s fallback condition as its own boolean rather than calling
  the Editor-only real method, so the two definitions can drift silently.
- **Content lints and resolver refusal families** (`ContentOwnershipLint`,
  `ContentInputCoverage`, `ContentFreshness`, `ContentStampIds`,
  `ContentSchema`, the twelve `*EntryResolver`s, `ContentDatabase.Validation`)
  are textual or id-level checks: they prove a JSON file's ids, shapes and
  ranges are internally valid and that the generated tree matches the
  current inputs, not that the generated ASSET's fields are correct, nor
  that authored values are balanced or narratively coherent. A hand-edited
  `.asset` with a correct id and a stale field is invisible to every one of
  them except the freshness timestamp check.
- **Art lints** (`StanceManifestValidation`, `HandAssembledArt`,
  `SpellVfxRecipeDrift`) are measurement and byte-identity checks: a small
  in-band drift, a deliberate bad update that also updates its own pin, and
  whether a chosen frame LOOKS right for its beat are all outside what any
  of them can see -- the capture fixtures below exist for the last one.

`GlobalStateLint` is a hard-coded table of 15 known globals; a new mutable
global added without a matching row is invisible to it, and it proves a
write is textually paired with a restore, not that the restore runs in every
order NUnit can choose.

### Process notes: two index sweeps and one banned command

Three sessions shared one working tree and one index. The rule that exists for
exactly this (`CLAUDE.md`: stage by explicit path, always) was not enough on
its own, because `git add <paths>` and `git commit` are two commands and
another session can run between them.

**What happened.** The shared index was swept twice during the fixer phase --
one session's `git add` was in flight when another committed. Separately, one
fixer used `git checkout HEAD -- <path>`, which this project bans outright; it
was scoped to that fixer's own file and the content was restored from a
snapshot, so nothing was lost. None of the three is recorded in any commit
message, which is itself worth noting: the only durable record is this
paragraph and the checks below.

**What was verified, rather than assumed.** Fixer A's four staged paths
(`Core/Content/ContentDatabase.Effective.cs`,
`Tests/PlayMode/Content/PrimaryPoolLookupTests.cs` and its `.meta`,
`Resources/Content/content_stamp.json`) are each in a fixer-A commit
(`42262d1c` for the first three, `4c751c9a` and `83d70363` for the stamp) and
in none of another fixer's -- `165c5746`'s file list was checked directly and
contains none of them. Every `.cs` under `Tests/` has its `.meta` committed
beside it: 386 and 386, with `comm` showing no unpaired file in either
direction; tree-wide under `Assets/`, 864 and 864. Every one of the 21 fixer
commits contains between one and nine files, all of them belonging to that
commit's stated fix.

**The mitigation, stated so it survives this session.** Stage and commit in ONE
shell invocation -- `git add <paths> && git commit -F <msg> -- <paths>` -- so
there is no window between them for another session's `add` to land in. The
explicit `-- <paths>` on the commit is the second half of it: even if a
foreign path did reach the index, the commit is still restricted to the paths
named. Every commit in this stage was made that way.

### Disproven, with the counter-evidence

One candidate was killed by running it rather than reading it, and it is worth
recording because the static-read version looked like a live bug.

- **"The pre-commit hook's ASCII scan flags every line of a committed
  `.ps1`."** By inspection it should: this repo's tracked `.ps1` files are CRLF
  on disk (`tools/test.ps1` has 699 CR bytes to 699 LF bytes, because
  `.gitattributes`' `* text=auto` sets no eol override for `.ps1`), and `\r` is
  outside the `[ -~]` printable range the hook's pattern allows. **Ran it:**
  `grep -n "[^ -~<TAB>]"` against the real tracked `tools/test.ps1` returns zero
  matches, and so does `printf 'a\r\n' | grep -n "[^ -~<TAB>]"`. Git Bash's
  grep strips `\r` before the pattern sees it, and the hook runs under that
  same `sh`. Recorded as **disproven with a stated portability caveat** rather
  than dropped: a POSIX grep that preserves `\r` could behave differently, which
  this Windows-only project does not have to care about today.

The four stage-3 disprovals (`ST3-RO-D1` through `D4`) are already recorded in
the stage-3 section above with their counter-evidence, and are not restated.

### Process notes: what went wrong in the running of it

- **Three rate-limit kills and three stalls** across the finder and fixer
  phases. The stalls all had one shape: an agent waiting on something it could
  not be woken from -- a background task, or a runner another agent held. The
  rule that came out of it is in this session's standing instructions and is
  worth repeating here: **never run a gate in the background.** Every Unity run
  in stage 5 was one foreground call with a long timeout, and both runners'
  lockfiles plus the process table were checked before each.

  a held runner. Both were waited out in a single foreground poll. No lockfile
  was ever deleted by hand; `test.ps1` removed two STALE lockfiles on its own,
  which is its documented behaviour.
- **`notes.md` is the filename, always.** Finder reports live at
  `scratchpad/hunt2/<stage>/<group>/notes.md` and nowhere else; a report under
  any other name is one the integrator does not find.
- **A batchmode frame is about two milliseconds, not a frame of wall clock.**
  The first version of `ButtonStateLifecycleTests` failed because a 40-frame
  wait does not cover a 140ms slide. Every timing wait in the new lifecycle
  classes is a wall-clock `Settle(seconds)` or the frame-budget shape
  `ReckoningPhaseTests` argues for, never a bare frame count. This is the
  single most reusable thing stage 3b learned.
