## 3. What is now in

### Phase 1 — tier and plus are separate axes (`e1792a6`)

`ItemDefinition.plus` was doing two jobs: `leather_coif_p10` was both "the best
coif in the game" and "a coif upgraded ten times". The baked axis is `tier` now,
and `plus` is a new field on the item **instance**.

Asset count stayed at **261** — baking both axes would have been 1,815 armour
pieces alone. **Item ids never changed**, so there is no save migration; old saves
load as all-plus-zero because `JsonUtility` reads a missing int as 0, which is the
correct reading of a save written before plus existed.

Armour gained tier adjectives (leather Ragged→Sovereign, steel Pitted→Sovereign,
silk Frayed→Sovereign) and both generators compose names through one shared
`ItemNaming`. Rarity bands (`Domain/Content/Rarity.cs`) colour item names in the
inventory, the choice cards, the paperdoll, the store and the Reckoning.

**Two things found rather than foreseen, both recorded in the commit:**

1. `ItemUpgrade.Apply` cannot go through float32. `1.4f` is really
   `1.39999997615814208984375`, so `20 * 1.4f` floors to **27, not 28** — a point
   silently missing at exactly the round numbers a player checks by eye. The curve
   is an integer percent. This is CLAUDE.md gotcha 5 from the other side.
2. Equipping must move **both halves**. Reading the displaced item's id without
   its plus, or reading either after `Set` has overwritten the slot, puts a +5
   sword back in the bag as a +0. That destroys value while leaving every count
   correct, so no count-based assertion would catch it.

Also fixed a **pre-existing flake** in `FullRunTests`: since weapons joined the
reward pool (`f0d9c5f`), the offer can hand out a second copy of the weapon the
Elite already dropped, so the bag legitimately still holds one after equipping.
The absolute count of 0 failed whenever that collision came up. It is a delta now.

### Phase 2 — reward tables that know what killed you (`baf5b7a`)

`ItemOfferTable.TargetPlus` was `floor - 1`, the only floor-sensitive system in
the game, and it treated a boss exactly like a corridor. `Domain/Rewards/
RarityTable.cs` owns that decision now; `ItemOfferTable` just picks three items
near a target it is handed.

`RollWeaponDrop` is gone — it sorted the catalogue by `attackBonus` and split it
in half, a derived pseudo-tier that ignored depth entirely and could never promise
what a boss would *not* drop. Both the choice screen and the guaranteed elite/boss
drop route through the one table now.

**The boss floor of tier 3 is absolute** and is the only hard guarantee in the
file — a boss never drops Common, at any depth. Pinned by sweeping every roll the
weight total can produce rather than by sampling.

Tier and plus roll **separately**: tier climbs with depth, plus does not know how
deep the run is at all (70% of normal drops are +0). Rolling them together would
average into "everything is slightly better than last floor".

`RunState.step` is the depth measure now — a continuous counter incremented once
per room resolved. The entrance deliberately does not count.

### Phase 3 — one continuous descent, and a difficulty curve (`d968d65`)

The map generates a **leg** at a time: eight columns off the step counter,
forever. Elite every 8th step, boss every 16th, boss wins. Forced columns are
width 1. Leg 1 ending on an elite and leg 2 on a boss is not special-cased — it
falls out of the leg length matching the elite period.

**The bug this introduced, kept as a regression test:** leg 1 ends on an
**elite**. Keying "generate the next leg" off "was that a boss" stranded the
player on the first leg — the final elite has no forward link, so `AdvanceRoom`
fell through to `IsFloorExhausted`, banked the run and sent them home. An endless
descent that ended at step 8. The end of a leg is asked **structurally** now.

`floor` survives as a counter of bosses beaten, **not** `step/16 + 1`. Deriving it
looked tidier and was wrong: the two agree only in real play, and every test that
pins a Boss into `roomLayout` puts a boss off the sixteen grid.

`Domain/Dungeon/DifficultyCurve.cs` is the half this phase could not skip — there
was **no** difficulty scaling anywhere. 5.5% per step and **linear, not
compounding**: at 5.5% compounding step 80 is ~72x, which outruns anything the
item ladder can answer (a fully honed top-tier set is worth roughly 4x a starting
one). Applied to health, attack, defense and break shields but **not speed** —
inflating speed would hand deep enemies extra turns through `SpeedScale`'s charge
rate, which was never built to absorb it. Rewards ride the same curve.

### Phase 4 — partial (`0ba07e9`)

`ResolveVictory` iterates `Save.ActiveSquad()` and `CharacterReward` carries an
explicit `SlotIndex`, so row *i* is squad slot *i* by construction. Downed squad
members get a dimmed, zero-gain row instead of vanishing and silently changing the
party's size between the fight and the results screen.

**Exp is still not split** — every fielded character receives the full amount.
Pre-existing; this makes it visible rather than changing it.

## 4. What comes next

**Two pieces, both SceneBuilder-side, neither large.**

### A. Battle UI polish

The structure is in (`8b8b9a5`) and rendered. What was knowingly left, all of it
polish rather than shape:

- The **turn timeline** is still the pre-existing initiative tracker, not restyled
  to the design's 78px acting chip / 64px upcoming chips with a pulsing `NOW`
  label and violet emphasis on hostile chips.
- **No animation at all**: the 140ms column slide-in, the pulsing target reticle
  and the `NOW` pulse are absent. The project already plays frame sequences from
  a folder for spells, which is the mechanism the design suggests.
- **Hover is uGUI's colour tint**, not the specced `1.02`/`1.03` scale. Note the
  root verbs deliberately keep the project's standard 105/95 `ButtonPressAnimator`
  and the wide rows deliberately do not — `ButtonPressAnimatorTests` encodes that
  exemption with the reason.
- **Panel gradients are flat mid-point fills.** Only the HP/MP bars get a real
  `UIGradient`. Bake sprites if the flat fills read poorly.
- **Items still resolve on the user.** The design's `targetMode` enum
  (`SELF | ONE_ALLY | ONE_ENEMY | ALL_ENEMIES | ALL`) is not built — the satchel
  chooses WHICH item, not who it lands on.

One consequence worth knowing before touching the stage: **party and enemy stage
nameplates are no longer drawn** (`Text.enabled = false`, set in `SceneBuilder`).
The enemy ones duplicated the plates; the party ones collided with the verb
column outright. The `Text` components stay and are still written, because the
stage tests read them. A squad of more than one therefore has no per-member HP on
the stage — `BaseMaxSquadSize` is 1 so nothing regresses today, but when it rises
the party plate should become one per fielded member rather than these coming
back.

### B. Phase 4's remainder — all SceneBuilder-side

- `RewardPortrait{i}` is built but never passed to `SetField`, so the controller
  has no handle on it and portraits are still coloured rectangles. Copy
  `CharacterSheetController`'s parallel `characterPortraitIds` /
  `characterPortraits` pattern; resolve by `definitionId`, not by index.
- `RewardsController.RowCount` is a hard 3. Build to 4, drive visible rows from
  `EffectiveMaxSquadSize()`.
- Extract one `ExpBarView` with `Set(level, exp, toNext, gainedFrom)`, used by
  both the Reckoning and the character sheet. `CharacterReward.BarFill01()` /
  `BarFillBefore01()` are dead code duplicating `RewardsController.DrawRow`'s
  inline maths — delete the pair, keep one implementation. Note that
  `CharacterRewardTests` (in `ItemOfferTests.cs`) covers them with eight tests
  that will need rehoming onto the new component.
- The character sheet shows no level or exp at all, so the two screens that should
  agree about progression share nothing.

## 5. Assumptions and known gaps

Stated plainly so any can be reversed cheaply:

- **`ItemUpgrade.PerPlus` is 4% per plus, so +10 is 1.40x.** Chosen against the
  tier curve: one tier is worth roughly 10% of a piece's total, so plus is a real
  but secondary axis. Above ~10% it would dominate tier and make the rarity bands
  decoration.
- **`DifficultyCurve` is 5.5% per step, linear.** See phase 3 above for why not
  geometric. It is the number most likely to want playtesting.
- **`RarityTable`'s distributions are weights out of 100 in one table each.** They
  are pinned exhaustively rather than sampled, so retuning them means editing
  numbers a test will immediately disagree with — which is the intent.
- **Plus never touches scaling grades or ability scores.** Grades belong to tier;
  ability scores feed derived stats that are already inside the scaled block, so
  scaling both would compound plus.
- **`ItemSetEntryResolver.FallbackAdjective` is empty for armour** (a set with no
  ladder keeps the bare piece name) and `"Plain"` for weapons (where the modifier
  already leads the name and a gap would show).
