# What was done, 5–6 September 2026, in plain language

## The problem we started with

Adding anything to the game took far longer than it should. The code itself was tidy, but
routine jobs touched too many places. To add one number to a skill you had to edit six files
that all repeated the same list of fields. To add one label to a screen you had to hand-write a
wiring line in a 1,400-line registry. To add one test you had to teach a list of name patterns
about it, and the test runner refused to start until you did. And before doing any of that, a
session was told to read about 2,400 lines of documents.

Then a second, sharper question came from the review: it is not how many files you touch that
matters, it is **how long it takes a person to add a monster, a spell or a character, give it
art, check it, and see it in the game.** Nobody had ever timed that.

## Pass one: fewer places to edit

Five audits ran in parallel, ranked the worst offenders, and 17 commits fixed them:

- Content records are stored once. A skill's fields used to be copied by hand through five
  layers on the way into the game; one of those copies had silently dropped two fields (the
  Black Ram transform and the spell-book fields), which is exactly the kind of bug that copying
  invites. Now eight of the eleven content types keep one record and adding a field is a
  three-file change.
- Screens wire themselves. Controller fields find their on-screen element by name; 372
  hand-written lines went away, and the build still refuses any field left unconnected.
- A test's area is the folder it sits in. The name-pattern list is gone; 44 of its last 47
  edits had been pure upkeep.
- The reading pile shrank. Old findings and finished plans moved to archive folders without
  deleting anything; the live debt register went from 1,633 lines to under 500.
- The field documentation inside the JSON files is now generated from the code, so it cannot
  go stale. Five stale claims were found and retired that way.

One thing was deliberately **not** done: trimming comments. About 38% of the code is comments,
but when sampled, four out of five explained a real reason. That is your call, not a defect.

## Pass two: make adding content fast, and prove it

First, three real tasks were timed in a throwaway copy, following the documentation as written,
with a clock on every step. Then tools were built, and the same three tasks were timed again.

| Task (from first edit to seeing it correct) | Before | After | Code edits needed |
|---|---|---|---|
| A monster with one ability | 6 min 00 s | 1 min 33 s | 1 → 0 |
| A spell on existing mechanics | 4 min 31 s | 2 min 27 s | 1 → 0 |
| A playable character | 5 min 24 s | 58 s | 2 → 0 |
| Rebuilding the content files | 65 s | 4 s | |

What made the difference:

1. **One command to look at one thing.** `tools/preview.ps1` with a monster, spell or
   character id checks the JSON, rebuilds content only if it is out of date, and either
   writes pictures or starts the fight in the Editor. It works whether the Editor is open or
   closed, and it never runs the full test suite.
2. **The rebuild itself got 15 times faster.** Every content asset was being imported one at
   a time; batching them took the step from 65 seconds to 4.
3. **You cannot test stale content by accident any more.** The build writes a stamp saying
   which inputs it was built from and which ids it wrote; a four-second test fails, naming the
   fix, whenever the JSON or the code has moved on since. Before, an edited JSON file and an
   old build were both green.
4. **Screenshots find new content on their own.** The picture tests used to hard-code which
   monsters and spells to photograph, so every new one meant a code edit. They now read the
   content list.
5. **Art comes with a recipe.** The slicer used to print a number for you to copy into the
   manifest by hand; it writes it now, and saves the exact command beside the sheet so the
   stills can be regenerated. Two actors are reproducible that way; six older ones whose stills
   were hand-picked are recorded as protected instead of pretending otherwise.
6. **A flaky test was actually diagnosed.** The spell-effect test failed at random; measured,
   the whole animation lasts 13 milliseconds at test speed and the test looked one frame too
   late. The suspect written in the register (a pooled object) was innocent.

Behind those, the safety nets the review demanded were added with real behaviour checks, not
just text searches: every skill effect is cast in a real fight and must move something; a
screen field bound to the wrong element fails the build naming both; content records cannot be
changed by a fight without a test noticing; and the test-discovery rules are proved against a
deliberately broken fixture.

An independent review of the whole delivery found nothing that falsifies the numbers, eleven
smaller issues, and all but one were fixed the same day.

## What is left for you

- `lightning_bolt` frame 5 differs from what its recipe produces. The shipped art was left as
  it is; re-running the tool would change it.
- All three characters use Shawn's portrait file, so previews of the other two show his face.
- The Editor watcher's "busy" state has never been seen in practice; the Editor was not open on
  this project while the work ran.
- Editing the content code now turns the fast test loop red until a 20-second rebuild. That is
  the price of the freshness check, and it is disclosed in the measurement logs.
- A genuinely new game mechanic still needs code. The tests now say exactly which four places.

Everything is on the `static-pilot` branch: 17 commits for pass one, 44 for pass two, with
the reasoning in each commit message and the timed logs under `docs/measurements/`.
